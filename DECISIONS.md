# Decisions

Cross-cutting calls, newest first. Terse: what, why, what it touches. STATUS.md says where the project is; this says why it is that way.

## 2026-10-03

### The Living Table is a standalone sealed app, not registered in Conjure Games yet
Owner: "Living table will be a seperate app but registered in conjure games. We may not have the registrations if we don't let's leave it out of conjure games all together and it will be stand alone." Nothing in the Conjure Games hub reads the `conjureGamesEntry` action today, so the app opens straight into its own window with no hub and no back-to-hub exit, and `package.json` no longer declares the action. The owner will design how games register later. Sealed: `"editStyle": "locked"` with `"editable": false` beside it (the manifest's rule for ConjureOS versions that read only `editable`), because the Living Table is a game shipped as-is and nothing may edit it ("no editing from the user period"). Locked does not limit connections: the AI and fullscreen permissions still work. Touches: `package.json` (0.9.0), `src/App.tsx`, `TableScreen.tsx`, the publish workflow. The conjureos-games repo is not touched.

### The old AI campaign mode is retired for predefined adventures
Owner: "retire all old for the new stuff. Bring in our example campaings for now to test." `LivingTable.tsx` (campaign list, campaign generator, hero creator, play screen, memory, inventory screens) and about 220 tests of that code are deleted, not hidden. The Rat Cellar, the Template adventure and the two test rooms are what a player starts from. Why: one game window, one set of rules, and no second code path to keep honest. Kept because the window or bench still imports them: `dm/turnSchema.ts`, `session/combat` and `hostileTurns`, `menu/commandMenu`, `render/doll` and `gearIcon`, `rules/rulebook`. Left for later cleanup: hub and campaign calls in `src/bridge/gamesApi.ts` and `ai.ts`, the old CSS, and stale comments.

### The game never states a credit price
Owner: "Don't promise credits anywhere. Just let the credit icon at the top of every app communicate that." No amount, price, "costs N credits" or "1 credit" anywhere a player can see. The platform's credit icon is the only signal. The e2e sweeps start, hero choice, character maker, board, sheet, every HUD tab and a DM answer for "credit" and price text and fails if it finds any; the release copy follows the same rule. Price copy that only the bench shows (`rules/rulebook.ts`, `menu/labels.ts`, `ui/dice.ts`) is still to be cleaned. Touches: every player-facing string, `CHANGELOG_NEXT.md`.

### The animated art ships as asset files, not in the package
The cast is about 6.3 MB of JSON and the KayKit library about 0.2 MB; the package limit is 5 MB. Owner: this is the owner's platform and the rule can be bent, and the sealed app type is where big games live. So both load through ConjureOS asset files, `window.__conjureos.assets.load(url, sha256)`, which refuses any file whose bytes do not match the hash; the table paints with still figures and the hand-drawn art first and swaps the animation in when it lands, and says so in the art status if a file is missing. The owner uploads the files once per project and pastes the address and hash into `table/host/assetFiles.ts` (a changed file has a new hash). The built page stays about 1.5 MB. Touches: `table/host/assetFiles.ts`, `gameArt.ts`, `scripts/assets/export-asset-files.mjs`.

### Saves live on the server
Owner: "On the server now." The game saves to games-db `game_saves` through the `gamesDb` remote action (key, kind, size and row limits enforced there). The device cache is a fallback: if the server is down the save stays on the device, says so, and goes up when the server is back. The cache is keyed by a hash of the signed-in player (`auth.whoami`), and a second player on the same device has the first player's cache put aside and never uploaded. On open, a player who has a save lands in their newest save. Touches: `table/host/gameStorage.ts`, `gameHost.ts`, `snapshot.ts`.

### The bench and the game share one window behind a TableHost
The window (`src/games/livingtable/table/`: `mountTable.ts`, `ui/`, the rules and DM modules) takes a `TableHost` (art, DM, storage, settings, files). The bench's `benchHost.ts` and the game's `host/gameHost.ts` are the only two differences. Why: before the port the bench had its own copy of the rules and the game had another, and a parity test compared them; now they are one function, so the parity test and the nine re-export shims under `scripts/asset-bench/` are deleted. The bench may read the game but `src/` may never name the bench (a guard test fails on the text `asset-bench` under `src/`). Touches: `scripts/asset-bench/`, `test/livingtable-asset-bench.test.ts`, `BENCH.md`.

### Dialogue text types out, pages, and never scrolls
Owner, after playing: text sometimes sat in a blue box and sometimes in a DM orange box with no clear difference, the two gave duplicate information, and long text scrolled. The ask: if one is high-level narration it must not show at the same time as the other; text prints one character at a time at a speed set in the game's settings; a box never grows large enough to scroll, longer text waits for a click; a click shows the rest of the page and the next click turns the page or closes the box. Built and e2e-checked: typing, paging, no scrolling, click to finish then turn, and the speed in the Settings tab (`textSpeed`, kept across a reload). The narration versus DM duplication is NOT covered by a test; the owner should look for it when playing. Touches: `table/ui/overlay.ts`, `table/host/gameSettings.ts`, the e2e dialogue spec.
